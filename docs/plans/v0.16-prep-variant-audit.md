# v0.16 Prep — Variant audit: every branch of the workflow, judged on evidence

Status: PLANNED. Blocking input to v0.16 Wave 1 ("exactly one best version of
every capability") — W1 may not adopt a capability until this audit has issued
its per-capability verdict. Companion research: `docs/research/skill-efficiency-gen5.md`.

## Why this exists

The unification plan assumed, implicitly, that the newest variant (windpath) was
the best one. That is not established. Five report-production variants and five
humanization variants exist across sessions; each moved *something* forward and
each carries flaws of its own. **Progression is not superiority.** This audit
compares them objectively so unification merges strengths — instead of merging a
fixed flaw with a new flaw, cancelling an existing strength, or (worst case)
merging only the flaws.

## Governance rules (encoded, not aspirational)

- **R1 — Recency is not evidence.** Every verdict cites a measurement or a
  transcript fact, never "it's the latest".
- **R2 — Adoption carries evidence.** Taking capability X from variant V also
  takes V's regression evidence for X. Claiming X fixes V₀'s flaw requires the
  flaw reproduced as a failing test first.
- **R3 — Loss ledger.** Every rejected alternative gets a written line: *what
  we lose by not taking it, and why that is acceptable.* No strength dies
  silently. The ledger is part of the output document, reviewed as a unit.
  Operator-approved strengths get extra protection: the compiled approvals
  ledger (`agenthwpx/docs/operator-approvals.md`) is a required input — a
  capability the operator explicitly approved cannot be dropped without an
  explicit ledger entry the operator sees.
- **R4 — Irreducible tradeoffs stay tradeoffs.** Where two variants are each
  right for different contexts (document family, run mode, operator presence),
  the unified pipeline keeps both behind an explicit switch and documents when
  each applies. Forcing a single winner is itself a merge error.
- **R5 — Differential benches only.** Full pipeline reruns are too slow to be
  the comparison unit. Variants are compared **only on the parts where they
  differ**, on shared fixed substrates (existing finished artifacts).
- **R6 — Per-form-family scoring.** The overfit axis is real and already
  measured once: T17 proved the school template (170 mm column) and the
  published compilation (163 mm) are *different formats*. At least three form
  families exist (소논문 한마당 제본용 / 2026 공식 탐구학술한마당 / 기록지-type).
  A value or rule learned on one family scores zero, not positive, on another
  until measured there.

## Comparison design — five differential benches

Substrates (fixed, already exist, no pipeline rerun): hawkes final
(`redabstract18_v5`/v8 line), windpath `output/v7/out.hwpx`, sambal
`Sambal_E_소논문_최신_사람화.hwpx`, one night-run artifact (enso-chaos-v3), plus
their `content.md` bundles.

**Bench 1 — Gate systems, cross-fired.** Run each gate system against every
substrate it did *not* grow up on: B's checkers (already done once = W5
campaign, reuse those numbers), D's `sim/gates.py`, E's declarative
`gates.yaml`. Count true positives / false positives / misses per system.
Known priors to confirm or kill: B fires ~200 `unbacked_numeral` FPs and
topic-scoped gloss HARDs on foreign topics; E's 12 forbidden-strings are
form-specific by design; **no variant's gates caught H5's subhead-density
problem — that is a shared miss and a candidate new mechanism.**

**Bench 2 — Humanization, same passages.** Fixed sample: 2–3 passages per
substrate (theory, methods, conclusion). Score all samples with H2's
`score_ai_tells` and H3's metrics (both are cheap instruments). Where a variant
transforms (H1, H2 full loop), run it on the same passages and measure: tell
reduction, fact invariance (fidelity audit), and **which flaws each instrument
is blind to** — H3 measured hawkes at z=+5.14 ending-comma yet the operator
still had to intervene on structure; H4's rules would have flagged what H3
missed? Test that claim on the H5 case.

**Bench 3 — Assembly fidelity + idempotency.** One form per family (R6). Run
A/C's COM-first path and E's preedit→assemble→postedit path on the same fill
payload. Measure: guide-text residue (T18 class), charPr integrity (T22 class),
margin fidelity (T16/T17 class), and double-run diff (idempotency — E claims
it, A/C never did).

**Bench 4 — Resume & state honesty, tabletop.** Kill-mid-run scenario walked
through each variant's actual files (no execution needed): what does a cold
session need to resume? Where does recorded state diverge from reality? Known
facts to weigh: C stalled at 5.5 with a finished artifact beside the stall
(state lies); E has no state at all (nothing to lie, nothing to resume from —
the conversation was the state); B's handoff v2 + receipts is the heaviest and
the most honest. Score: steps-to-resume, divergence risk, weight carried.

**Bench 5 — Provenance cold-read.** For two numbers and one figure per
substrate: can a reader with no session context reconstruct *why that value*?
C's research pack vs E's empty `research/` is the extreme pair; B's receipts
sit between. This bench prices what E's leanness actually cost.

## Complexity axis (counted, not felt)

Per variant: files touched per report, distinct concepts an operator must know,
gates per run, operator interventions observed in transcripts (E: 7 report
rounds + 4 poster rounds with ≥3 operator corrections; D: 3 named convergence
artifacts; C: 4 approval gates + 1 stall). Interventions are read from session
transcripts — they are data, and the reason full reruns aren't needed.

## Output

`docs/research/variant-audit.md` containing:

1. **Decision matrix** — capability × variant, verdict + evidence pointer per
   cell. Capabilities: form preprocessing, assembly engine, gate architecture,
   state/resume, provenance, humanization measurement, humanization
   transformation, layout/density judgment, poster generation.
2. **Loss ledger** (R3) — every rejected alternative, what it costs, why
   acceptable.
3. **Mode decisions** (R4) — tradeoffs kept as switches, with the context rule
   for choosing (e.g. *if* the audit finds state machines earn their weight only
   in unattended runs: heavy state for night mode, lean build.yaml for
   supervised — that is the hypothesis to test, not the conclusion).
4. **Shared-miss list** — flaws no variant catches (H5 structure-density is
   already one confirmed member); these become new-mechanism candidates for W1,
   each needing a still-catches example per the calibration rule.
5. **Per-form-family applicability table** (R6).

W1 consumes the matrix: each "one best version" decision cites its row. A
capability with no verdict does not move.
