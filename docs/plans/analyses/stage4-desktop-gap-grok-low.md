# Stage 4 desktop gap (G1–G5)

Read-only survey against `docs/plans/stage4-gui.md`, the research note’s synthesis and slice list, `docs/desktop-code-map.md`, `docs/runtime-protocol-v0.md`, DocumentView layout, and the named desktop sources plus `desktop/scripts/*.test.mjs`. Renderer freeze is assumed: no live COM preview claims.

The existing Tauri shell already implements most of the *layout* Stage 4 wants (StructureTree | TextView or PagePreview | ReviewQueue + History; ReceiptPanel and VerificationBar shared). The remaining work is honesty of provenance, CLI method aliases that are still GAP on the wire, and a few product rules (hash-bound approve without auto-apply, IME freeze of the gate, inspect of `forbidden` anchors).

## 2. Does the desktop know `com` and `native_com_session`?

**Mostly as untyped strings, not as a product path.**

- **`plan/propose` always sends `backend: "preedit"`** (`runtime.ts` ~197–199). There is no UI or wrapper to propose `backend: "com"`. Protocol: propose accepts `com` only when `backends.com` is available; apply of a com plan is one `com_backend.py edit` batch; receipt `evidence.class` is `native_com_session` (`runtime-protocol-v0.md` ~413–414, ~675–687, ~700–705).
- **Grep in `desktop/` TypeScript/JS:** **zero** occurrences of the token `native_com_session`. Evidence is `evidence.class` as `string` (`types.ts` ~361) and rendered verbatim (`ReceiptPanel.tsx` ~186–189). Smoke asserts `structural_only` (`smoke.ts` ~782, ~3437). PagePreview comments that rasters are `structural_only` / `proofGrade: "none"` (`PagePreview.tsx` ~28–31).
- **`capabilities.backends`:** `StructureTree` iterates **whatever keys** the runtime sends (~116–131), so a `com` row would appear as unavailable/available without special copy. `Capabilities.supportedBackends` exists on the type (`types.ts` ~201) but G1 does not let the user pick it.
- **Comments, not handling:** `actions.ts` cites `com_backend.py` validate-whole-plan discipline (~384) and `unsupported_backend` on propose failure (~912). `PagePreview` treats **`com_busy` / `needs_hancom` as render-prepare refusals**, which is Hancom *convert*, not the edit backend.
- **Conclusion:** the shell can *display* a future com receipt’s backend and evidence class. It cannot *author* a com plan, cannot test `native_com_session` in headless scripts, and must not imply COM apply from the current ReviewQueue.

## 4. Risks

- **Approve-and-apply collapse** hides the GitHub “review ≠ merge” lesson. Testers may think hash binding is skipped because one button does both; the runtime still binds, but UX trains the wrong model.
- **Cached `before` vs `read-region`:** if inspect/text cache is stale relative to `boundSha256`, the hunk can show a before the Runtime will not apply. Reverse path already avoided this; G1 review should not regress.
- **`verify/*` temptation:** VerificationBar already warns. A green “re-verify” that called nothing would be the bar’s stated failure mode.
- **COM confusion:** `com_busy` on prepare looks like “we use COM for edits.” Mixing convert COM with `backend: "com"` / `native_com_session` in copy will leak unfreeze claims.
- **IME:** seat Enter is guarded; ReviewQueue and global vermilion are not. Mid-syllable approve is the Stage 4 acceptance item most likely to ship as a paper pass and fail in Korean.
- **Agent projection vs plan JSON parity:** GUI and CLI must emit the same plan JSON. Editing unsupported ops in the queue is refused today (good); silently dropping fields would fail acceptance.
- **Headless tests vs IME/render:** `npm test` does not prove composition or Card4/5 GUI (`desktop-code-map.md` Focused verification). Task 1 must not be declared “IME done” from Node tests alone.
- **Events vs History:** operators looking for G5 in DocumentView will find candidates, not `events.jsonl`. Splitting those records is correct per the code map; product copy should say so.
