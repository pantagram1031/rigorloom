# v0.16 — Absorb the engine, modularize the rest, ship modules separately

Status: PLANNED. Owner: orchestrator (Claude) plans and reviews; codex implements
slices; opus judgment pass before each merge.

Companions:
- `docs/plans/v0.16-prep-variant-audit.md` — Phase 0.C, gates all capability adoption
- `docs/research/skill-efficiency-gen5.md` — Phase 0.B (done), grounds Wave 5

## Context for a reader with no session history

Rigorloom's capability currently lives in **three separate code homes that have
drifted apart**, and the most recent production work happened in the one that is
*not* upstream:

| home | what it is | state |
|---|---|---|
| `dev/rigorloom` (this repo, public) | stage machine, ~30 deterministic checkers, render proof ladder, personalization store, privacy gate | tag `v0.15.0-alpha`; README still advertises v0.11.3; suite 636 pass on `v015-first-cert` |
| `.claude/skills/hwp-master` (separate repo) | the actual HWP/HWPX **editing engine** — `xml_backend` (COM-free assembly), `com_backend`, `form_inspect`, `fill_report`, `tidy_hwpx`, `style_diff`, `eqn.py`, `layout_qa`, `charpr_check`, `render_calibrate` | tag `v0.3.0`, 246 tests, clean |
| `Downloads/agenthwpx` (private workspace) | where three real reports were actually built in 2026-07/08, plus `reportkit/`, an award-corpus benchmark, and `kb/trouble-table.md` | 19 paths uncommitted |

The three 2026-07/08 reports (`report-sambal-e-robot`, `report-hawkes-bike-allocation`,
`report-windpath-hanmadang`) were produced **without** the rigorloom state machine —
progressively so. sambal used the full 6-stage machine and stalled at the understanding
gate; hawkes ran to stage 6 but grew a report-local toolbox under `sim/`; windpath
dropped the state machine entirely and shipped on `build.yaml` + a declarative
`gates.yaml` + versioned `output/v1..v7` folders. Everything those runs learned —
T15 through T22, the idempotent preedit/postedit XML pattern, the
`form_profile.json` shape, the 204-report layout corpus — is stranded in the
private workspace. **Which of those ways was better is an open question the
variant audit answers; this plan does not presume.**

**Rigorloom is not a report-only name.** It carries a lot of report machinery today
because that is what got built first, not because the kernel is report-shaped. This
plan makes rigorloom *the general HWP document engine*, absorbs hwp-master into it,
and turns everything else — report, style, personalization — into modules that live in
this repo but **ship as separate installable packages**.

## Target shape

One repo. One core. N modules behind one contract.

```
  ┌──────────────────────────────────────────────────────────────┐
  │  RIGORLOOM (this repo)                                       │
  │                                                              │
  │  CORE — general HWP/HWPX document engine                     │
  │    form recognition · blank/placeholder detect+fix           │
  │    table/equation/image insertion · spacing · margins        │
  │    render proof ladder · non-destructive discipline          │
  │    studio (base viewer) · privacy_scan · module registry     │
  │                                                              │
  │  modules/  — same contract for every one, present and future │
  │    report          run modes · report checkers · corpus      │
  │                    benchmark · poster · example works        │
  │    style           translationese removal · voice            │
  │                    consistency · AI-tell scoring             │
  │    personalization profile store · preference packs          │
  └──────────────────────────────────────────────────────────────┘
              │ one repo, many distribution bundles
              ▼
     rigorloom-core   rigorloom-report   rigorloom-style   …
     (base product)   (installs on top)  (installs on top)
```

Development is monorepo — one test suite, one CI, atomic cross-module changes.
Distribution is per-module — a skillshop buyer takes core alone, or core plus
whichever modules they want, and modules light up extra capability when present.

## Non-goals

- Rewriting the editing engine. hwp-master's code becomes core by history-preserving
  merge, not reimplementation.
- Splitting into multiple repos. Rejected: the sync cost is real and the packaging
  boundary is achievable without it.
- Shipping any corpus material. `kb/corpus/` holds ~200 real student names and IDs
  plus three volumes with live-format API keys. It never leaves the private
  workspace, in any derived form, at any wave.
- Claiming universal Linux render fidelity. That constraint is owned by the v0.15
  certification plan and is unchanged here.
- Pre-deciding capability winners. Adoption follows the variant audit's matrix,
  under its governance rules (R1–R6).

## Wave 1 — Converge (two lanes)

Wave 1 runs in two lanes with different gates, so measured facts move while the
audit finishes.

### Lane F — facts (audit-independent; may start alongside 0.C)

These are measurements, not preferences. No matrix row needed.

**F1. Backfill the field lessons** from `agenthwpx/kb/trouble-table.md` into
`docs/trouble-table.md`, each with a failing-before/passing-after test:

| id | lesson | lands in |
|---|---|---|
| T16 | Hancom stacks body top = top margin **+ header height**; feeding a measured print-face position straight into `top` double-counts it | core |
| T17 | School templates declare a 170 mm column; the published compilation is 163 mm. A template does not reproduce its own compilation | core |
| T18 | Deleting guide-text paragraphs by charPr colour must **protect table / secPr / ctrl paragraphs**; unprotected deletion collapsed a layout into 21 pages with a 20-line hole | core |
| T20 | The builder only scans `bundle/figures/`; the path convention was implicit in code | report |
| T21 | Concurrent sessions: each `--kill-stale` (`taskkill /F /IM Hwp.exe`) kills the *other* session's live Hwp instance | core |
| T22 | A naive `'id="34"' not in header` guard false-matches a paraPr id; guard *and* verification must use `<hh:charPr\b[^>]*\bid="34"` | core |

Engine-owned tests land in the hwp-master repo now (they ride the Wave 2 merge);
T20 lands rigorloom-side.

**F2. T21 real fix** — per-machine lock; refuse a name-scoped kill while another
owner's instance is live. Manual `tasklist` inspection is not shippable.

**F3. Version-drift reconciliation** — README (claims v0.11.3), CHANGELOG,
`SUMMARY.md`, capability matrix vs tag `v0.15.0-alpha` and what actually ships.

**F4. Duplication inventory** — enumerate every capability that exists in two
homes with two behaviors (`figstyle.py` ×2, gate runners ×3, preedit scripts ×2,
scaffolders ×2…). Inventory only; resolution is Lane V's job with the matrix in
hand.

### Lane V — verdicts (blocked on the 0.C matrix)

For each capability in the audit matrix, adopt the winning mechanism upstream
under the audit's governance: the adoption cites its matrix row (R1), carries
the source variant's regression evidence (R2), writes its loss-ledger entry for
the rejected alternatives (R3), and becomes a **mode** rather than a winner
where the audit says the tradeoff is irreducible (R4).

Capabilities on the docket (winners intentionally unnamed here):

- **Edit shape** — three-phase XML (preedit → assemble → postedit, idempotent)
  vs COM-first vs hybrid; possibly per form family (R6).
- **Gate architecture** — central checker registry vs per-workspace declarative
  `gates.yaml` vs hybrid (registry mechanisms, declared values). Must answer the
  W5-campaign false-positive record either way.
- **State & resume** — full stage machine vs receipts-only vs stateless. If the
  audit finds the machine earns its weight only unattended, it becomes the
  report module's *night mode*, not the default.
- **Humanization stack** — how instrument (H3), transformer (H1/H2), rulepack
  (H4), and structural checks compose; which gate is load-bearing.
- **Provenance floor** — what the minimum evidence trail is for a delivered
  document (windpath's empty `research/` priced by Bench 5).
- **Shared-miss mechanisms** — new gates for flaws *no* variant caught
  (subhead-density is the confirmed member), each shipped with a still-catches
  example per the calibration rule.

**Wave 1 acceptance:** Lane F all tested and merged; every Lane V adoption has
matrix row + regression evidence + ledger entry; no capability exists in two
places with two behaviors (F4 inventory zeroed).

## Wave 3 — The module contract

The load-bearing wave. Everything after it — report, style, personalization, and
anything added later — is "just another module."

### 3.1 Contract

A module is `modules/<name>/` with a `module.yaml` declaring what it contributes:

```yaml
name: report
requires: { rigorloom: ">=0.16" }
provides:
  checkers:      # registered into the check registry
  cli:           # subcommands under the main entry point
  pack_types:    # personalization pack types it defines
  run_modes:     # run-mode definitions (see 3.2 — hosts R4 mode decisions)
  studio_panels: # UI contributions (see 3.4)
  skill:         # SKILL fragment + references, merged by the installer
  playbooks:     # stage/task playbooks
```

Design inputs, both mandatory reading before the contract is drafted:

- The 0.A judgment on `codex/v013-extension-packs` (a prior data-pack
  install/verify/resolve mechanism, 1,280 lines with tests; merge was HELD
  pending an agreed v0.13.1 policy boundary — 3-tier merge policy,
  `constants_allowlist` excluded from extension types, dual scoring, `explain`
  command, effect_summary bound to (id,version,effect_hash)). Absorb its
  verify/resolve semantics or explicitly retire it — not both mechanisms.
- **v0.12-W1's existing `modules.yaml` (16 typed contracts) + compose resolver**
  (aliases full-report / pre-researched / verify-only / assemble-only, with the
  mandatory-gate floor and forged-receipt rejection). That machinery composes
  *pipeline stages*; this wave's modules are *distribution/packaging units* — a
  different axis. The contract must either extend that vocabulary or rename one
  of the two ("module" cannot mean both things in one repo), and must not break
  the compose resolver's gate-floor guarantees.

Rules:

- **Core never imports a module.** Dependency points one way; modules register
  through the registry; core has no name-level knowledge of any module.
- **Absence is not failure.** Core's suite runs green with every module
  disabled. CI runs both matrix points (core-only, all-modules) — added
  **before** anything moves.
- **Presence is integration.** Enabling a module surfaces its checkers, CLI,
  panels, and modes with no further configuration.
- **Adding a module later requires no core change.** Proven by a trivial
  throwaway module in this wave.

### 3.2 Run modes

The audit's R4 outputs land here as first-class contract objects: a run mode
bundles a state policy (stage machine / receipts / stateless), gate set, and
operator-presence assumptions. Expected shapes — *supervised lean* (windpath-
style) and *unattended night* (stage machine + heavy provenance) — but the
audit's mode decisions, not this plan, fix the list. Modes are declared by
modules (`run_modes:`), selected per workspace, and visible in the capability
probe.

### 3.3 Move report behind the contract

Everything report-shaped moves into `modules/report/`: stage machine and
`pipeline_ctl`, report-semantic checkers (`check_saeteuk`, `check_scorecard`,
`check_understanding`, `check_claims`, `check_corpus`, `check_sources`,
`check_refs`, `content_audit`), corpus benchmark, `poster_build`, `reportkit`'s
scaffolder, example works.

Two questions decide each item: does it mention reports, students, or schools;
and would a person editing a government form ever run it. "Yes / no" moves.
Genuinely general machinery **stays in core**: render proof ladder,
`render_probe`, `render_cert`, `feature_extract`, `privacy_scan`,
`form_extract`, layout checks, `doc_backend`, the receipt/verdict contract.
Ambiguous items (`check_numbers`, `check_figdata`, `check_units`) stay in core;
the report module narrows them via packs rather than forking them.

Example works (the three 2026-07/08 reports plus `examples/workspace`) become an
opt-in examples pack inside the report module — never installed by default,
never a test dependency, `privacy_scan`-clean before packaging.

### 3.4 Studio: base in core, extended by modules

Studio stays in **core** as a general document surface: open a document, see its
structure, see what is fillable, preview the render, inspect verdicts. Modules
extend it declaratively through `studio_panels` — report adds stage progress,
gate verdicts, proof-grade badge; absent module, absent panels. Studio never
learns a module's name. The 0.A judgment on `spike/studio-web-editor` decides
whether the editor spike ships in core-studio or parks.

### 3.5 Per-module packaging

`scripts/package_module.py --module <name>` emits a standalone installable
bundle (SKILL fragment + references + scripts + declared requirements). Extend
the existing base+overlay installer (`scripts/sync_local.py` + manifest) to
base+modules+overlay — no second mechanism.

**Acceptance:** core suite green with all modules disabled; report bundle
installs onto a core-only install and lights up without editing core; the
throwaway module proves zero-core-change extension.

## Wave 4 — Style and personalization as modules

### 4.1 Personalization

Exists today as `personalization_ctl.py`, `.local/personalization`, eight pack
types, a signed store, `RIGORLOOM_PROFILE_ROOT`. Two corrections:

- Schema is named `report-pipeline/personalization-v1` with report-flavored
  pack types. Split: **general packs** (identity, writing voice, figure style,
  backends, policy floors) declared by this module; **report packs** (`saeteuk`,
  `report_structure`, `gloss_allowlist`, `constants_allowlist`) declared by the
  report module through `pack_types`.
- Personal data is *conventionally* outside the repo; make it *structurally*
  outside: one documented store, one CLI, export/import for machine portability,
  and a hard gate failing any build whose artifacts contain store content.

`privacy_scan` stays in **core** — repo hygiene, not personal state.

**Acceptance:** create profile → export → clean machine → import → drive a
build, with the repo never having held its content.

### 4.2 Style

Consolidate `humanization_ctl.py`, `prose_fidelity.py`, `check_style.py`,
`style_extract.py`, `docs/humanization.md`, `agent.humanizer.template.md` into
one module whose internal composition follows the audit's humanization-stack
verdict (which instrument gates, which transformer runs, where structural
checks sit).

Boundary, stated in the module docs: translationese removal, voice consistency,
form-rule compliance. **Not AI-detection evasion.**

Rules come from packs, not code. The award-corpus rulepack (checkable rules —
e.g. the eight no-hedge cases) is a *pack instance* shipped by the report
module; a non-report user supplies their own.

## Wave 5 — Landscape, evals, then the skill surface

Order matters: 0.B's strongest finding is **evals before skill surface**, and
the eval scenarios should come from real usage — so the usage survey moves here,
ahead of packaging (it was originally last, which its own risk note called
backwards).

### 5.1 HWP usage landscape

Survey the real population of Korean HWP forms — government filings, school
administrative forms, corporate templates, contracts, application forms, 공문 —
recording what each family demands: table density, nested tables, form fields,
seals/stamps, headers, multi-section documents, fixed-position layout. Output:
`docs/research/hwp-usage-landscape.md` with a prioritized family list, and a
**blank-form corpus** (official templates only, no real filled documents).

### 5.2 Eval scenarios first

From the corpus, write eval scenarios per family (open → recognize → fill →
verify), with expected-behavior rubrics. Baseline each scenario with *no* skill
loaded. These evals are the acceptance instrument for 5.3 and the regression
suite seed for Wave 6.

### 5.3 Skill surface (gen-5 rules from 0.B)

- Router SKILL.md per distribution bundle, far under 500 lines; module skill
  fragments merged at install — a core-only buyer never sees report vocabulary.
- All operations behind scripts returning JSON verdicts; `inspect` returns
  structure only, never body text — the hwp-master rule becomes a guarantee.
- Capability probe (Hancom? certified renderer? live backends? enabled modules?
  active run mode?) injected via dynamic context at skill load; one entry point
  built on `render_probe` + `backend_precheck`.
- Freedom map documented per operation: fill/assembly/postedit = low freedom
  (exact CLI, "do not modify"); form diagnosis, layout judgment = high freedom.
- Frontmatter levers wired deliberately: `disable-model-invocation` on heavy
  flows, `paths:` gating on `*.hwp/*.hwpx`, `context: fork` for long
  deterministic subflows, `allowed-tools` for the skill's own scripts.
- Trouble-table knowledge ships as *behavior* (guards inside scripts) first,
  reference file second, SKILL.md body never.

**Acceptance:** every 5.2 eval passes with the skill loaded, beats its no-skill
baseline, and the loaded-token footprint per task is measured and reported.

## Wave 6 — Prove, bound, release

### 6.1 Measured generality

Run the form-recognition benches on the 5.1 corpus per family: anchor
extraction recall, blank/placeholder detection (guide text, colour-coded
instructions, placeholder names, empty table cells, ruled lines), fill
fidelity, non-destructive guarantee under repeat runs. Honest per-family
reporting; failures included.

### 6.2 Fix or bound

Each failure either gets a mechanism fix (with regression test) or becomes a
**documented capability boundary** shipped in the skill surface — "this family
is unsupported" stated up front, never a silent gap. If a family proves
report-shaped assumptions run deep, the product claim narrows here, before
anything is sold.

### 6.3 Release

- Tag `v0.16.0`; cut bundles (`rigorloom-core`, `-report`, `-style`,
  `-personalization`) at the same version.
- `privacy_scan` HARD-clean on every bundle; zero corpus-derived content
  (checked, not assumed).
- CHANGELOG + migration notes (from the old hwp-master install and from
  pre-module rigorloom).
- Positioning check on all shipped text: the style capability is
  translationese removal / voice consistency / form-rule compliance — never
  AI-detection evasion.

## Ongoing — keep sharpening

Every real document produced after Wave 1 is a holdout. When it exposes a gap:
fix the mechanism, add the regression test, add the trouble-table row. The
calibration rule binds — every relaxation ships with a still-catches example.

## Risks

- **The contract is the whole bet.** If it leaks — core importing a module, a
  checker reaching into report state — the packaging boundary silently dies.
  Guard: core-only CI matrix point added before anything moves.
- **Two surgeries close together.** W2 merges a repo in; W3 rearranges
  everything. Wave 1 Lane F lands first so both move against a stronger suite.
- **Audit verdicts may be uncomfortable.** The audit can demote mechanisms this
  repo spent waves building (e.g. the stage machine to an optional night mode).
  The plan commits to following the matrix anyway; overriding it requires a
  written counter-measurement, not preference.
- **Boundary disputes in 3.3.** Two-question test; still ambiguous → stays in
  core, narrowed by packs.
- **Generality may narrow the claim.** 6.2 exists precisely so that happens
  before sale, not after.
