## Premise correction — read this before the tables below

exact input HWPX files (19) they came from" — one screenshot per input,
each showing a documented visual defect. That set does not exist.

- The acceptance-evidence directory itself
  (`private/private-desktop-preview-2b712ff/`) contains **2 PNGs** total

- The 44-PNG / 19-HWPX counts only appear when globbing the **whole**

  `tests/corpus/forms/{converted,grant}/` fixtures, 2 copies of a synthetic
  operator-authored form, 3 generated candidate/artifact files (edited
  copies of a corpus form from smoke/MCP runs), 2 copies of the corpus form
  used as an MCP source, and the 1 private personal document.
- `ACCEPTANCE.md` and the `smoke/report-page.json` / `report-overlay.json`
  phases state explicitly that Desktop is **not wired to any own renderer**;

## Worst two, visually diffed against the Hancom reference render

**1. kstartup, candidate page 5 — pagination collapse (new-to-notes mechanism).**
Candidate page 5 shows three separate reference sections overlapping in
one page image: "3. 사업 추진계획 및 사업화 계획" (empty product-comparison
boxes), "3. 과제 세부추진 개발계획" (Gantt-style schedule table), and a
budget/성과목표 table — text and table borders drawn on top of each other.
The scoreboard's per-page detail shows why: candidate page 5 carries 103
detected text lines against 10 on the matching reference page. This is a
genuine renderer bug, not a documented limit: `own-render-notes.md` bases
pagination on the top-level `hp:vertpos` cache restarting at each page
start (plus a quarter-page floor); a run of several consecutive
table-heavy sections defeats that heuristic and at least two real page
breaks are missed, which also explains the 20-vs-22 page-count mismatch —
the loss happens once, here, and later pages stay offset by 2 (candidate
page 20 corresponds to reference page 22, confirmed visually below).

**2. kstartup, candidate page 20 / reference page 22 — a whole shape class renders as nothing.**
The reference page's two dark, rounded, numbered section-header badges
("❶ 수집·이용에 관한 사항", "❷ 기업(신용)정보의 파기") are **completely
absent** from the candidate — not just unstyled, no box, no label, no
trace at all. This is stricter than the documented behavior: item 3 of
`own-render-notes.md`'s *Named fidelity limits* says `hp:ole`, `hp:chart`,
`hp:container`, and "the drawing shapes" fall back to a grey outlined box
labelled 그림/도형. On this same page a plain rectangular `hp:container`
placeholder ("도형") **does** render correctly as that documented grey box
— so the gap is specifically this numbered-badge shape variant silently
skipping the placeholder fallback it should get, not a page-level failure.
Everything else on this page (both tables, all body text, the consent
paragraph, the signature line) matches the reference closely.

Both findings are on the same document, at opposite ends of the page range,
and independent of each other — the pagination collapse doesn't touch page
20's content, and page 20's missing badges don't affect line counts.

**gianmun-byeolji-1ho, for contrast:** side-by-side with its Hancom
reference render, the single page is visually near-identical — text
position, the red 직인 box, the grey band, the horizontal rules, and the
footnote all match. The low `text_line_iou_mean` (0.021) despite a
reasonable `ssim_mean` (0.881) is a line-pairing artifact of the scoring
tool on this form's layout, not a visible rendering defect, and is already
consistent with the scoreboard's declared own-uncertified caveats — no new
mechanism here.

## Does our renderer line already cover these?

- **Pagination collapse under consecutive dense tables**: not covered.
  `own-render-notes.md`'s pagination section describes only the vertpos-
  restart heuristic and the quarter-page floor; it does not name this
  failure mode. **New mechanism.**
- **Numbered-badge shapes rendering as nothing instead of the documented
  grey placeholder**: partially covered — the shape *category* (drawing
  shapes / `hp:container`) is named in the fidelity limits, but the
  documented behavior (grey 도형 box) does not hold for this specific shape
  variant, which the same page's plain `hp:container` box shows is
  otherwise implemented. **A gap inside a documented category, worth a
  note update, not a wholly new category.**

## Fixture decision

No new `engine/tests` fixture was added. `kstartup-jiwon-sincheongseo-
saeopgyehoekseo.hwpx` is already a tracked corpus fixture with a Hancom
reference PDF in `tests/corpus/forms/render/`, and is already exercised by
`render_scoreboard.py --corpus`. Both findings above are reproducible today
from existing corpus/reference data — no Codex asset is needed and none was
copied. Turning either finding into a hard regression assertion (exact page
count, or a badge-shape presence check) needs threshold calibration against
the rest of the corpus first, which is outside this verification task's
scope and risks tuning a gate to one document (see the repo's
calibration-no-overfit rule).
